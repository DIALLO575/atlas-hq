## First implementation slice

- `packages/connectors/linear/src/contract.ts` records the Linear API endpoints, allowed OAuth scopes, and capability-to-scope mapping. Read access is the default; issue and comment creation use their targeted scopes. Broad `write` and `admin` are excluded, and writes are not enabled in the runtime contract.
- `oauth.mjs` builds a user-actor OAuth authorization URL with PKCE S256, validates HTTPS callback URLs (loopback HTTP only for local development), restricts scopes, and exchanges authorization codes server-to-server using form encoding. It validates the token response and returns only the required token fields; errors are allowlisted and do not include provider response bodies.
- `oauth-state.mjs` signs a 15-minute state bound to one ATLAS workspace and actor, stores only its SHA-256 hash through an atomic-store interface, checks the signed state against the HttpOnly cookie and verified callback actor/workspace, then consumes it once. Migration `20261024114533_atlas_linear_oauth_states.sql` supplies the durable, RLS-enabled server-only ledger and is recorded as applied in the official project history.
- `graphql-client.mjs` is a minimal no-store GraphQL transport. It does not log, cache, or serialize the bearer token into an application response. Provider errors are mapped to safe categories.
- `workspace-access.mjs` is a fail-closed policy predicate: the authenticated actor must match the queried workspace member, role must be `owner`, `admin`, or `member`, and requested ATLAS workspace must equal the linked workspace. Only owners/admins may manage a connection. Callers must obtain identity and membership from the verified ATLAS server session/database; caller-supplied role values are not authority.

This remains a non-live integration. The start route verifies the Supabase session and owner/admin membership, requires a fixed callback URI, stores a one-time state hash, and sets short-lived HttpOnly/Secure/SameSite cookies. Callback exchange is disabled unless `LINEAR_OAUTH_CALLBACK_ENABLED` is explicitly `true`, the token keyring is valid, and the connection table is reachable; default configuration remains disabled. When enabled, it verifies the Linear viewer and organization IDs, then stores only AES-256-GCM ciphertext bound by AAD to both ATLAS and Linear actor/workspace IDs. The connection row is unique to the ATLAS actor and workspace, has no client grants or policies, and uses versioned compare-and-swap writes. Refresh is serialized by a durable database claim; disconnect tombstones the row locally before attempting RFC 7009 provider revocation. The three migrations are recorded in official Supabase history under the versions listed above. No Linear credentials or live API calls are configured. Migration application alone does not enable or prove a Linear connection. The client transport is a base for the following read-only API slice, not a general write API.

## Read-only transport correction (2026-10-24)

The initial `graphql-client.mjs` accepted arbitrary GraphQL documents despite `writesEnabled: false`. The isolated follow-up `fix/linear-graphql-readonly` adds a GraphQL-aware lexical scan before transport: it rejects mutations, subscriptions, invalid/ambiguous operation selection, and multi-operation documents without a uniquely matching `operationName`. It ignores comments and string/block-string contents while classifying operations, and includes tests proving rejected documents never call `fetch`. Multiple read operations are allowed only with an explicit operation name. This is a narrow operation-kind guard, not a full GraphQL validator; Linear remains responsible for schema and document validation. The targeted connector test file passes 11/11 locally. No Linear API request or live deployment was made.

## API behavior checked against Linear documentation

- Linear recommends OAuth 2.0 for third-party applications. Its authorization URL is `https://linear.app/oauth/authorize`; send `response_type=code`, callback, scope, and CSRF-protected state. PKCE uses `code_challenge` with `S256`.
- Authorization codes are exchanged by form POST to `https://api.linear.app/oauth/token`; the callback URI must match. PKCE sends the original verifier. Access and refresh tokens are returned; access tokens expire after 24 hours and must not be treated as durable API keys.
- The public API is GraphQL at `https://api.linear.app/graphql`; OAuth bearer credentials are sent in the `Authorization` header.
- Supported narrow scopes documented by Linear include `issues:create` and `comments:create`; `admin` is described as full admin access and should be avoided unless essential. This contract does not request `write` or `admin`.

Sources: [Linear OAuth 2.0 authentication](https://linear.app/developers/oauth-2-0-authentication), [Linear GraphQL getting started](https://linear.app/developers/graphql), [Linear API and webhooks](https://linear.app/docs/api-and-webhooks). Documentation checked 2026-10-24.

## Encrypted token store slice (2026-10-24)

- `token-vault.mjs` encrypts access and refresh tokens independently with AES-256-GCM, 96-bit random nonces, 128-bit tags, and AAD containing provider, schema version, both ATLAS IDs, both Linear IDs, token type, and key ID. Missing, malformed, unknown, or mismatched keys fail closed.
- Server key configuration names: `LINEAR_OAUTH_TOKEN_KEYS` (JSON key-ID to base64 32-byte key map) and `LINEAR_OAUTH_TOKEN_KEY_ID` (current key ID). Keep the whole keyring in a server secret manager. Rotation requires adding a new key version, selecting it as current, re-encrypting each actor connection with the existing row version, verifying successful CAS, then retiring an old key only after no stored rows reference it. No key value belongs in Git, logs, or client configuration.
- Migration `20261024114556_atlas_linear_oauth_connections.sql` adds one credential row per `(ATLAS workspace, ATLAS actor)`, references live `workspace_members` with cascade on membership removal, enables RLS with no client policy/grants, grants the service role only SELECT/INSERT/UPDATE, and restricts save/revoke RPC execution to service role. Database version CAS makes key re-encryption, reconnect and logical revoke race-safe. Reconnect clears the revoke marker only on a version-matched update. Removing an ATLAS workspace membership deletes its local ciphertext row but does not revoke the grant at Linear; provider-side revocation remains a separate action.
- The callback checks the current owner/admin membership and state actor, consumes the one-time state, checks the connection table is deployed before exchange, requests `read` only, calls the fixed Linear GraphQL endpoint to verify `viewer.id` and `viewer.organization.id`, then persists the actor-specific encrypted record. The current official Linear schema includes `Query.viewer: User!` and `User.organization: Organization!`; the OAuth guide documents `viewer` identity queries. See [Linear OAuth 2.0](https://linear.app/developers/oauth-2-0-authentication), [Linear GraphQL](https://linear.app/developers/graphql), and the [current official schema](https://raw.githubusercontent.com/linear/linear/master/packages/sdk/src/schema.graphql). If identity or persistence fails after exchange, it makes best-effort fixed-endpoint revocation for both tokens and returns only a fixed status. The callback remains disabled by default.
- Unit tests exercise ciphertext, tamper detection, wrong key/context, key rotation, actor and workspace isolation, member denial, safe callback success/failure, and no exchange when disabled. CI #377 applies these migrations only to its ephemeral PostgreSQL 17 fixture and tests role grants, RLS, membership binding, logical revoke, and concurrent version CAS.
- Official Supabase history records all three migrations as applied at the versions listed above. No OAuth code was exchanged and no real Linear API request was made during this implementation. OAuth callback activation requires an explicit separate release decision after CI and application-level review. A real managed secret-store setup and runtime validation against a real Linear/Supabase tenant remain outstanding.

## Refresh and disconnect lifecycle (2026-10-24)

- `POST /api/apps/linear/connect/refresh` accepts same-origin form requests only. It resolves the actor from `getUser()` and a current `owner`/`admin` membership row, binds the lookup to that user's ATLAS workspace, and does not return tokens. A still-valid access token is left alone; refresh begins only within two minutes of expiry.
- Before contacting Linear, the route calls the server-only `atlas_linear_claim_refresh` CAS. The claim is a durable single-flight lock across processes. It has no automatic timeout: a timeout, malformed success, or network failure can mean Linear consumed and rotated the refresh token, so the gate stays closed and the route reports `refresh-uncertain`. An administrator must disconnect/reconnect to recover; automatic retries are deliberately absent.
- Linear refresh uses the documented `grant_type=refresh_token` form at `https://api.linear.app/oauth/token`. A successful response is checked for Bearer tokens, expiry, and exactly the existing `read` scope. The new pair is encrypted before `atlas_linear_complete_refresh` atomically replaces the ciphertext, increments the version, and clears the claim. Ordinary key rotation/reconnect CAS writes cannot bypass an active claim. If `invalid_grant` is returned, the local connection is tombstoned. If provider success is observed but storage completion is uncertain, the code attempts a local tombstone and best-effort revocation of the new pair.
- A completed refresh that loses a simultaneous disconnect cannot restore the row: disconnect increments the version, clears the claim, and tombstones locally first. The completing refresh then fails CAS and attempts to revoke the newly returned pair.
- `POST /api/apps/linear/connect/disconnect` performs the same session, owner/admin, workspace, and Origin checks. Local logical revocation happens before provider requests. The route submits both encrypted token values separately to the fixed `https://api.linear.app/oauth/revoke` endpoint using RFC 7009's `token` and `token_type_hint` fields. Only HTTP 200 is reported as confirmed; Linear documents 400/401 failures, including an already-revoked token as a possible 400, so other responses remain `unconfirmed`. The ciphertext tombstone is retained so a later explicit disconnect request can retry provider revocation.
- The versioned migration `20261024114631_linear_oauth_refresh_gate.sql` adds the durable claim and server-only RPC grants. Official history records it as applied; the CI migration chain and cross-session concurrency script run only in ephemeral PostgreSQL.
- Linear documentation checked for refresh and revoke semantics: [OAuth 2.0 authentication](https://linear.app/developers/oauth-2-0-authentication). In particular, refresh returns a new refresh token; the documented 30-minute grace window does not justify automatic retries after an ambiguous local result. No live credential exchange or revocation was performed.

## First server-side read API slice (2026-10-24)

- `GET /api/apps/linear/read?workspaceId=…&resource=teams|projects|issues[&after=…]` exposes only three named, fixed GraphQL query documents. The client cannot submit query text, operation names, page sizes, or an access token. Each request is authorized against a verified Supabase user and current `workspace_members` row; a member may read only through that same actor's own active, encrypted connection. There is no workspace-shared token.
- The service decrypts only on the server, requires the `read` scope, refreshes an expired/near-expiry credential through the existing durable refresh gate, and reloads the connection before querying. The GraphQL response includes `viewer.id` and `viewer.organization.id`; both must match the linked Linear actor and workspace before any result is returned.
- Pagination is cursor-based and bounded to one page of 25 records per HTTP request. The response includes `hasNextPage`, `endCursor`, and `incomplete`; it never silently claims a partial page is complete. Cursors are opaque, limited in length, and cannot alter the query.
- Linear's GraphQL `RATELIMITED` response (including HTTP 400 with `extensions.code`) and HTTP 429 map to a safe 429 response. A valid upstream `Retry-After` or documented rate-limit reset header is converted to bounded seconds and returned as `Retry-After`; the server does not automatically retry. HTTP 401, other provider errors, partial GraphQL errors, malformed payloads and identity mismatch fail closed without returning provider bodies or bearer tokens.
- Behavioral fixtures cover teams/projects/issues, cursor/page bounds, missing or removed membership, actor and workspace mismatch, refresh-before-read, wrong Linear organization/actor, malformed payload, 401, GraphQL `RATELIMITED`, and retry delay propagation. No real Linear or Supabase API was contacted.
- Current official sources checked: [GraphQL getting started and error handling](https://linear.app/developers/graphql), [pagination](https://linear.app/developers/pagination), [rate limiting](https://linear.app/developers/rate-limiting), and [Linear's current GraphQL schema](https://raw.githubusercontent.com/linear/linear/master/packages/sdk/src/schema.graphql). The slice is tested against fixtures only; schema drift and a real tenant's permissions remain unverified.
